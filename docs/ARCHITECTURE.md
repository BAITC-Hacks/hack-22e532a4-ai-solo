# Архитектура BaqBaq после аудита

Один FastAPI-процесс, SQLite и статический frontend. Оригиналы организатора подключаются локально.

```text
Upload -> DOCX/PDF/XLSX parser -> DocumentVersion / SourceSpan
                                   | exact SQLite
                                   v
Registry -> local embeddings -> candidate graph -> coverage / overlap / authority
   | live extraction + matching            |
   +---------------------------------------+-> Finding -> ReviewDecision -> report(run_id)

Question -> bounded model tool loop -> comparison-scoped Gateway
         -> source validation -> deterministic exact citations -> answer + request trace
```

## Канонические данные и история

DocumentVersion содержит хеш, сторону, редакцию и оригинал. SourceSpan содержит точный текст и локатор. FunctionAssertion — интерпретация, а не установленная истина.

RunSnapshot закрепляет состав документов, конфигурацию поиска, ID извлечённых функций и проверенных кандидатов. API результата/отчёта принимает run_id; старый запуск доступен после нового. ReviewDecision хранится отдельно и экспортируется вместе с комментарием. Интерфейс показывает историю запусков и решений.

## Извлечение и соответствия

Registry ориентируется на содержимое заголовков и таблиц, не на известные номера. Модельный режим извлекает атомарные функции пакетами с проверкой точных цитат и источника владельца. Результаты прошедших валидацию пакетов кешируются.

FastEmbed работает на CPU, multilingual MiniLM выдаёт 384-мерные векторы. embedding_cache — производные значения по хешу текста и имени модели; отсутствие записи вызывает повторное вычисление. Lexical режим предусмотрен явно. Ошибка выбранного encoder не скрывается переходом на другой метод.

Граф FunctionMatch может хранить несколько пар для split/merge. Offline-правила — эвристические кандидаты; live-сопоставление проверяет переданные кандидаты моделью. Непопадание в модельный shortlist не является доказательством отсутствия функции. В снимке сохраняются размер обследованного набора и лучшие кандидаты.

## Доказательства и полнота

Ссылки проверяются по comparison_id; инструменты исторического запуска проверяют также документный снимок. Совпавший текст с установленным владельцем может получить MATCH; изменённые смысловые соответствия остаются UNKNOWN до ручной проверки.

Плохое извлечение или отсутствие функций на стороне даёт partial и явный finding недостаточности данных. При неполном комплекте потенциальная потеря преобразуется в недостаточность данных. Экспорт partial разрешён с предупреждением.

Одинаковый владелец с исполнением и контролем одного объекта — потенциальное совмещение. Разные владельцы сами по себе не доказывают конфликт. Правила не заменяют полный анализ независимости и подчинённости.

## Агент

Инструменты: search_sources, read_source, find_functions, compare_sources, check_coverage, get_analysis. Gateway ограничивает сравнение и источники; агента нельзя заставить прочитать чужой source ID.

Live-цикл: максимум 6 шагов, 6 инструментов за шаг; timeout 45 секунд, один retry на API-вызов. Ответ — JSON со статусом и разрешёнными прочитанными IDs. Невалидный ответ отклоняется. Цитаты вставляются из exact-хранилища. Проза модели остаётся интерпретацией и не считается автоматически доказанной.

Agent trace сохраняется по request_id; analysis trace — по run_id. Это журнал инструментов и времени, не скрытые рассуждения. UI получает прогресс из backend, а не имитирует этапы таймером.

## Проверка

24 документных сценария идут через public API; тесты модельного транспорта не подменяются live-метриками. Все проверки используют отдельное временное состояние. Браузерный сценарий проверяется отдельно.

Нет MCP, распределённых очередей, enterprise IAM или автоматического crash recovery. Идемпотентность поддержана для создания сравнения; весь анализ ещё не является идемпотентной задачей.
